# Reviews

Виджет отзывов для сайтов клиник и консоль управления им. Отзывы, клиники и
врачи загружаются из личного кабинета агрегатора MyReviews и выводятся на
сайте клиента отдельным веб-компонентом.

## Состав

Монорепозиторий pnpm: пять приложений и четыре общих пакета.

| Приложение         | Назначение                                                                 |
| ------------------ | -------------------------------------------------------------------------- |
| `apps/console-api` | API консоли: вход, привязка агрегатора, клиники и врачи, настройки виджета |
| `apps/widget-api`  | Публичный API виджета: клиники, врачи, лента отзывов                       |
| `apps/sync-worker` | Загрузка данных от агрегатора по расписанию и по запросу консоли           |
| `apps/console`     | Консоль управления, SPA                                                    |
| `apps/widget`      | Виджет для сайта клиента, веб-компонент `<reviews-widget>`                 |

| Пакет                 | Назначение                                               |
| --------------------- | -------------------------------------------------------- |
| `packages/database`   | Схемы Mongoose и разбор имен для поиска, общие для служб |
| `packages/aggregator` | Клиент MyReviews и шифрование его токена                 |
| `packages/config`     | Проверка переменных окружения при старте                 |
| `packages/testing`    | Подставная модель Mongoose для проверок                  |

Службы не обращаются друг к другу: общее у них — база и пакеты. Обработчик
синхронизации не слушает порт вовсе, а запросы консоли забирает из базы.

### Как связаны части

```
MyReviews ──► sync-worker ──► MongoDB ◄── console-api ◄── консоль
                                 ▲
                                 └────── widget-api ◄── виджет на сайте клиента
```

Клиент привязывает кабинет MyReviews в консоли: пароль обменивается на токен
и не сохраняется, в базу ложится только зашифрованный токен. Обработчик
синхронизации переносит организации и отзывы. Виджет обращается в свой API по
публичному ключу кабинета; доступ ограничен списком доменов.

## Консоль и виджет

В консоли три раздела: «Обзор», «Клиники» и «Врачи».

- **Обзор.** Привязка кабинета MyReviews и ручной запуск синхронизации, код
  для сайта со списком разрешенных доменов и условия отбора отзывов (пока это
  наименьшая оценка). Домены и условия сохраняются сразу при изменении.
- **Клиники** и **Врачи.** Таблицы с поиском по имени и числом загруженных
  отзывов. Переключатель «В виджете» скрывает запись: ее нет в фильтре
  виджета, а ее отзывы не попадают в ленту. Синхронизация флаг не сбрасывает,
  она задает его только при создании записи. Здесь же выдается код вставки для
  страницы каждой клиники и каждого врача.

Условия отбора и скрытие применяются при чтении ленты. Отзывы из базы не
удаляются, а изменение действует с ближайшего обращения виджета, без повторной
синхронизации.

### Код вставки

| Атрибуты `<reviews-widget>` | Что выводит виджет                                  | Где взять код                                |
| --------------------------- | --------------------------------------------------- | -------------------------------------------- |
| `api-key`                   | Все отзывы кабинета с фильтром по клиникам и врачам | «Обзор», карточка «Код для сайта»            |
| `api-key`, `target-id`      | Отзывы одной клиники или одного врача, без фильтра  | «Клиники» или «Врачи», кнопка «Показать код» |

Оба вида работают только на доменах из списка разрешенных. В ленту клиники не
входят отзывы о ее врачах: MyReviews не связывает врачей с клиниками.
Идентификатор в `target-id` привязан к записи: если клиника или врач пропадет
из MyReviews и появится снова, код нужно взять заново.

## Стек

- **Среда:** Node 24, pnpm 12 (через corepack), TypeScript 6, Turborepo
- **Службы:** NestJS 11, Mongoose 9, MongoDB 8
- **Консоль:** React 19, React Router 8, TanStack Query 5, Zod 4, CSS Modules
- **Виджет:** Lit 3 (`@lit/task`, `@lit/context`), стили в теневом DOM
- **Сборка:** Vite 8, `nest build` для служб
- **Проверки:** Vitest 4, ESLint 10, Prettier 3
- **Безопасность:** Argon2id для паролей, AES-256-GCM для токенов агрегатора,
  JWT для сессий консоли, `@nestjs/throttler` для ограничения частоты запросов

## Требования

- Node 24 или новее
- Docker — для MongoDB при разработке и для развертывания
- pnpm ставить отдельно не нужно: версия закреплена полем `packageManager`,
  достаточно `corepack enable`

## Локальный запуск

```bash
cp .env.example .env      # заполнить TOKEN_ENCRYPTION_KEY и JWT_SECRET
docker compose up -d mongo
pnpm install
pnpm dev
```

`pnpm dev` поднимает три службы и оба фронтенда; общие пакеты собираются
автоматически, потому что задачи объявлены зависимыми.

| Что               | Адрес                   |
| ----------------- | ----------------------- |
| Консоль           | `http://localhost:5174` |
| Песочница виджета | `http://localhost:5173` |
| API консоли       | `http://localhost:3010` |
| API виджета       | `http://localhost:3011` |
| MongoDB           | `localhost:27017`       |

### Ключ виджета в песочнице

В репозитории атрибут `api-key` пуст, потому что ключ выдается под конкретный
кабинет:

```html
<reviews-widget api-key=""></reviews-widget>
```

Без ключа песочница выводит «Не задан ключ виджета». Чтобы виджет заработал:

1. Зарегистрироваться в консоли (`http://localhost:5174`) и привязать кабинет
   MyReviews.
2. В карточке виджета добавить `localhost` в список разрешенных доменов —
   иначе API ответит 403.
3. Скопировать оттуда же ключ и вставить его в
   [`apps/widget/index.html`](apps/widget/index.html).

Чтобы посмотреть виджет одной клиники или врача, добавьте в элемент атрибут
`target-id` из кода, выданного в разделах «Клиники» и «Врачи».

Ключ публичен по устройству: он виден в исходниках страницы клиента, а доступ
ограничивает список доменов. Тем не менее в репозиторий его коммитить не
стоит — перед фиксацией правок значение лучше вернуть к пустому.

Песочница обращается к API по адресу из `VITE_WIDGET_API_URL`, то есть на
соседний порт. Так и задумано: виджет обязан ходить на чужой источник, иначе
браузер не отправит заголовок `Origin`, и API отклонит запрос.

## Команды

Все команды выполняются из корня и раскладываются Turborepo по пакетам.

| Команда             | Что делает                             |
| ------------------- | -------------------------------------- |
| `pnpm dev`          | Службы и фронтенды в режиме разработки |
| `pnpm build`        | Сборка всех пакетов                    |


## Переменные окружения

Все переменные задаются единым файлом `.env` в корне — включая переменные
сборки фронтендов. Образец со списком и пояснениями — `.env.example`.

Значений по умолчанию нет: незаданная или негодная переменная останавливает
запуск службы, которой она нужна. Тихая подстановка скрывала бы ошибку
настройки до первого обращения клиента.

| Переменная                                                 | Кому нужна                 |
| ---------------------------------------------------------- | -------------------------- |
| `MONGODB_URI`                                              | всем трем службам          |
| `TOKEN_ENCRYPTION_KEY`                                     | console-api, sync-worker   |
| `JWT_SECRET`                                               | console-api                |
| `CONSOLE_API_PORT`                                         | console-api                |
| `WIDGET_API_PORT`                                          | widget-api                 |
| `AGGREGATOR_BASE_URL`                                      | console-api, sync-worker   |
| `WIDGET_SCRIPT_URL`                                        | console-api (код вставки)  |
| `VITE_CONSOLE_API_URL`, `VITE_WIDGET_API_URL`              | сборка фронтендов          |
| `MONGO_INITDB_ROOT_USERNAME`, `MONGO_INITDB_ROOT_PASSWORD` | docker compose             |
| `MONGO_PORT`                                               | docker compose, разработка |

Три последние переменные читает не приложение, а `docker compose`. Учетные
данные базы создаются при первом ее запуске и входят в `MONGODB_URI`; в
боевом файле compose этот адрес собирается из них же. `MONGO_PORT` публикует
базу на хост только при разработке — в боевой среде порт наружу не выводится.

Адреса API вшиваются в бандлы при сборке: задним числом их не сменить.
Собранная без адреса консоль обращалась бы к собственному поддомену, а виджет
пошел бы за отзывами на сайт клиента — поэтому без этих переменных боевая
сборка намеренно падает.

## Развертывание

Один `Dockerfile` дает три образа служб и два каталога статики. Статику
отдает nginx хоста, контейнеров под нее нет.

### Службы

```bash
docker compose -f docker-compose.prod.yml up -d --build
```

Поднимаются MongoDB, оба API и обработчик синхронизации. Порты API
публикуются только на `127.0.0.1` — наружу их выводит nginx. Порт базы не
публикуется вовсе. У контейнеров API есть `HEALTHCHECK`: он опрашивает
`GET /health` и отличает зависший процесс от работающего.

### Статика

Каталоги собираются отдельными целями с боевыми адресами API:

```bash
docker build --target console-dist \
  --build-arg VITE_CONSOLE_API_URL=https://api.console.reviews.stackra.ru \
  --output type=local,dest=/home/deploy/apps/reviews/console .

docker build --target widget-dist \
  --build-arg VITE_WIDGET_API_URL=https://api.widget.reviews.stackra.ru \
  --output type=local,dest=/home/deploy/apps/reviews/widget .
```

### Требования к nginx

Три условия, без которых сборка формально работает, а продукт — нет.

**1. Реальный адрес клиента.** Службы доверяют одному прокси, и ограничение
частоты запросов считает обращения по адресу клиента. Без заголовка все
посетители всех клиентских сайтов попадут в один счетчик и начнут получать 429.

```nginx
proxy_set_header Host $host;
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
proxy_set_header X-Forwarded-Proto $scheme;
```

Именно `$proxy_add_x_forwarded_for`: он дописывает настоящий адрес справа, и
подставленное клиентом значение в расчет не идет.

**2. CORS для файла виджета.** Код вставки — `<script type="module">`, а
модульные скрипты браузер всегда запрашивает в режиме CORS, в отличие от
обычных. Без заголовка виджет не загрузится ни на одном клиентском сайте.

```nginx
location / {
    add_header Access-Control-Allow-Origin *;
    try_files $uri =404;
}
```

**3. Возврат к `index.html` для консоли.** Маршрутизация браузерная, поэтому
без этого обновление страницы на `/signin` даст 404.

```nginx
location / {
    try_files $uri $uri/ /index.html;
}
```

### Адреса

| Служба         | Поддомен                         |
| -------------- | -------------------------------- |
| Консоль        | `console.reviews.stackra.ru`     |
| API консоли    | `api.console.reviews.stackra.ru` |
| Скрипт виджета | `widget.reviews.stackra.ru`      |
| API виджета    | `api.widget.reviews.stackra.ru`  |

`WIDGET_SCRIPT_URL` должен указывать на поддомен скрипта виджета. Это
единственное значение, которое расходится по сайтам клиентов: оно попадает в
код вставки, который консоль выдает каждому из них.

## Как работает синхронизация

Полный прогон выполняется дважды в сутки, в 03:00 и 15:00 по Москве (часовой
пояс задан явно, время контейнера значения не имеет). Запрос из консоли
подхватывается опросом раз в 15 секунд.

Прогон защищен от потери данных: захват не дает двум процессам работать над
одним кабинетом, за один раз нельзя удалить больше половины отзывов, а пустой
ответ агрегатора при непустой базе прерывает прогон вместо очистки.
