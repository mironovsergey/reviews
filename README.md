# Reviews

Виджет отзывов для сайтов клиник и консоль управления им. Отзывы, клиники и
врачи загружаются из личного кабинета агрегатора MyReviews и выводятся на
сайте клиента отдельным веб-компонентом.

## Состав

Монорепозиторий pnpm: пять приложений и четыре общих пакета.

| Приложение         | Назначение                                                                 |
| ------------------ | -------------------------------------------------------------------------- |
| `apps/console-api` | API консоли: вход, привязка агрегатора, клиники и врачи, настройки виджета |
| `apps/widget-api`  | Публичный API виджета: клиники, врачи, лента отзывов                       |
| `apps/sync-worker` | Загрузка данных от агрегатора по расписанию и по запросу консоли           |
| `apps/console`     | Консоль управления, SPA                                                    |
| `apps/widget`      | Виджет для сайта клиента, веб-компонент `<reviews-widget>`                 |

| Пакет                 | Назначение                                               |
| --------------------- | -------------------------------------------------------- |
| `packages/database`   | Схемы Mongoose и разбор имен для поиска, общие для служб |
| `packages/aggregator` | Клиент MyReviews и шифрование его токена                 |
| `packages/config`     | Проверка переменных окружения при старте                 |
| `packages/testing`    | Подставная модель Mongoose для проверок                  |

Службы не обращаются друг к другу: общие у них только база и пакеты. Обработчик
синхронизации не слушает порт вовсе, а запросы консоли забирает из базы.

### Как связаны части

```
MyReviews ──► sync-worker ──► MongoDB ◄── console-api ◄── консоль
                                 ▲
                                 └────── widget-api ◄── виджет на сайте клиента
```

Клиент привязывает кабинет MyReviews в консоли: пароль обменивается на токен
и не сохраняется, в базу ложится только зашифрованный токен. Обработчик
синхронизации переносит организации и отзывы. Виджет обращается в свой API по
публичному ключу кабинета; доступ ограничен списком доменов.

## Консоль и виджет

В консоли три раздела: «Обзор», «Клиники» и «Врачи».

- **Обзор.** Привязка кабинета MyReviews и ручной запуск синхронизации, код
  для сайта со списком разрешенных доменов и условия отбора отзывов (пока это
  наименьшая оценка). Домены и условия сохраняются сразу при изменении.
- **Клиники** и **Врачи.** Таблицы с поиском по имени и числом загруженных
  отзывов. Переключатель «В виджете» скрывает запись: ее нет в фильтре
  виджета, а ее отзывы не попадают в ленту. Синхронизация флаг не сбрасывает,
  она задает его только при создании записи. Здесь же выдается код вставки для
  страницы каждой клиники и каждого врача.

Условия отбора и скрытие применяются при чтении ленты. Отзывы из базы не
удаляются, а изменение действует с ближайшего обращения виджета, без повторной
синхронизации.

### Код вставки

| Атрибуты `<reviews-widget>` | Что выводит виджет                                  | Где взять код                                |
| --------------------------- | --------------------------------------------------- | -------------------------------------------- |
| `api-key`                   | Все отзывы кабинета с фильтром по клиникам и врачам | «Обзор», карточка «Код для сайта»            |
| `api-key`, `target-id`      | Отзывы одной клиники или одного врача, без фильтра  | «Клиники» или «Врачи», кнопка «Показать код» |

Оба вида работают только на доменах из списка разрешенных. В ленту клиники не
входят отзывы о ее врачах: MyReviews не связывает врачей с клиниками.
Идентификатор в `target-id` привязан к записи: если клиника или врач пропадет
из MyReviews и появится снова, код нужно взять заново.

## Стек

- **Среда:** Node 24, pnpm 12 (через corepack), TypeScript 6, Turborepo
- **Службы:** NestJS 11, Mongoose 9, MongoDB 8
- **Консоль:** React 19, React Router 8, TanStack Query 5, Zod 4, CSS Modules
- **Виджет:** Lit 3 (`@lit/task`, `@lit/context`), стили в теневом DOM
- **Сборка:** Vite 8, `nest build` для служб
- **Проверки:** Vitest 4, ESLint 10, Prettier 3
- **Безопасность:** Argon2id для паролей, AES-256-GCM для токенов агрегатора,
  JWT для сессий консоли, `@nestjs/throttler` для ограничения частоты запросов

## Требования

- Node 24 или новее
- Docker: для MongoDB при разработке и для развертывания
- pnpm ставить отдельно не нужно: версия закреплена полем `packageManager`,
  достаточно `corepack enable`

## Локальный запуск

```bash
cp .env.example .env      # заполнить TOKEN_ENCRYPTION_KEY и JWT_SECRET
docker compose up -d mongo
pnpm install
pnpm dev
```

`pnpm dev` поднимает три службы и оба фронтенда; общие пакеты собираются
автоматически, потому что задачи объявлены зависимыми.

| Что               | Адрес                   |
| ----------------- | ----------------------- |
| Консоль           | `http://localhost:5174` |
| Песочница виджета | `http://localhost:5173` |
| API консоли       | `http://localhost:3010` |
| API виджета       | `http://localhost:3011` |
| MongoDB           | `localhost:27017`       |

### Ключ виджета в песочнице

В репозитории атрибут `api-key` пуст, потому что ключ выдается под конкретный
кабинет:

```html
<reviews-widget api-key=""></reviews-widget>
```

Без ключа песочница выводит «Не задан ключ виджета». Чтобы виджет заработал:

1. Зарегистрироваться в консоли (`http://localhost:5174`) и привязать кабинет
   MyReviews.
2. В карточке виджета добавить `localhost` в список разрешенных доменов,
   иначе API ответит 403.
3. Скопировать оттуда же ключ и вставить его в
   [`apps/widget/index.html`](apps/widget/index.html).

Чтобы посмотреть виджет одной клиники или врача, добавьте в элемент атрибут
`target-id` из кода, выданного в разделах «Клиники» и «Врачи».

Ключ публичен по устройству: он виден в исходниках страницы клиента, а доступ
ограничивает список доменов. Тем не менее в репозиторий его коммитить не
стоит: перед фиксацией правок значение лучше вернуть к пустому.

Песочница обращается к API по адресу из `VITE_WIDGET_API_URL`, то есть на
соседний порт. Так и задумано: виджет обязан ходить на чужой источник, иначе
браузер не отправит заголовок `Origin`, и API отклонит запрос.

## Переменные окружения

Все переменные задаются единым файлом `.env` в корне, включая переменные
сборки фронтендов. Образец со списком и пояснениями лежит в `.env.example`.

Значений по умолчанию нет: незаданная или негодная переменная останавливает
запуск службы, которой она нужна. Тихая подстановка скрывала бы ошибку
настройки до первого обращения клиента.

| Переменная                                                 | Кому нужна                 |
| ---------------------------------------------------------- | -------------------------- |
| `MONGODB_URI`                                              | всем трем службам          |
| `TOKEN_ENCRYPTION_KEY`                                     | console-api, sync-worker   |
| `JWT_SECRET`                                               | console-api                |
| `CONSOLE_API_PORT`                                         | console-api                |
| `WIDGET_API_PORT`                                          | widget-api                 |
| `AGGREGATOR_BASE_URL`                                      | console-api, sync-worker   |
| `WIDGET_SCRIPT_URL`                                        | console-api (код вставки)  |
| `VITE_CONSOLE_API_URL`, `VITE_WIDGET_API_URL`              | сборка фронтендов          |
| `MONGO_INITDB_ROOT_USERNAME`, `MONGO_INITDB_ROOT_PASSWORD` | docker compose             |
| `MONGO_PORT`                                               | docker compose, разработка |

Три последние переменные читает не приложение, а `docker compose`. Учетные
данные базы создаются при первом ее запуске и входят в `MONGODB_URI`; в
боевом файле compose этот адрес собирается из них же. `MONGO_PORT` публикует
базу на хост только при разработке. В боевой среде порт наружу не выводится.

Адреса API вшиваются в бандлы при сборке: задним числом их не сменить.
Собранная без адреса консоль обращалась бы к собственному поддомену, а виджет
пошел бы за отзывами на сайт клиента. Поэтому без этих переменных боевая
сборка намеренно падает.

## Развертывание

Один `Dockerfile` дает три образа служб и два каталога статики. Статику
отдает nginx хоста, контейнеров под нее нет.

Обычная выкладка выполняется тегом версии, см. раздел «Автоматическая
выкладка». Команды ниже нужны для первой установки сервера и ручного
вмешательства.

### Службы

```bash
docker compose -f docker-compose.prod.yml up -d --build
```

Поднимаются MongoDB, оба API и обработчик синхронизации. Порты API
публикуются только на `127.0.0.1`: наружу их выводит nginx. Порт базы не
публикуется вовсе. У контейнеров API есть `HEALTHCHECK`: он опрашивает
`GET /health` и отличает зависший процесс от работающего.

### Статика

Каталоги собираются отдельными целями с боевыми адресами API:

```bash
docker build --target console-dist \
  --build-arg VITE_CONSOLE_API_URL=https://api.console.clinicstars.ru \
  --output type=local,dest=/home/deploy/apps/reviews/console .

docker build --target widget-dist \
  --build-arg VITE_WIDGET_API_URL=https://api.widget.clinicstars.ru \
  --output type=local,dest=/home/deploy/apps/reviews/widget .
```

### Требования к nginx

Три условия, без которых сборка формально работает, но продукт остается
нерабочим.

**1. Реальный адрес клиента.** Службы доверяют одному прокси, и ограничение
частоты запросов считает обращения по адресу клиента. Без заголовка все
посетители всех клиентских сайтов попадут в один счетчик и начнут получать 429.

```nginx
proxy_set_header Host $host;
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
proxy_set_header X-Forwarded-Proto $scheme;
```

Именно `$proxy_add_x_forwarded_for`: он дописывает настоящий адрес справа, и
подставленное клиентом значение в расчет не идет.

**2. CORS для файла виджета.** Код вставки подключает виджет через
`<script type="module">`, а модульные скрипты браузер всегда запрашивает в
режиме CORS, в отличие от обычных. Без заголовка виджет не загрузится ни на
одном клиентском сайте.

```nginx
location / {
    add_header Access-Control-Allow-Origin *;
    try_files $uri =404;
}
```

**3. Возврат к `index.html` для консоли.** Маршрутизация браузерная, поэтому
без этого обновление страницы на `/signin` даст 404.

```nginx
location / {
    try_files $uri $uri/ /index.html;
}
```

### Адреса

| Служба         | Поддомен                     |
| -------------- | ---------------------------- |
| Консоль        | `console.clinicstars.ru`     |
| API консоли    | `api.console.clinicstars.ru` |
| Скрипт виджета | `widget.clinicstars.ru`      |
| API виджета    | `api.widget.clinicstars.ru`  |

`WIDGET_SCRIPT_URL` должен указывать на поддомен скрипта виджета. Это
единственное значение, которое расходится по сайтам клиентов: оно попадает в
код вставки, который консоль выдает каждому из них.

## Автоматическая выкладка

Версия выкладывается тегом:

```bash
git tag v1.2.0
git push origin v1.2.0
```

Тег запускает workflow [«Выкладка»](.github/workflows/deploy.yml):

1. Проверки: типы, линтер, форматирование, тесты.
2. Сборка образов `console-api`, `widget-api`, `sync-worker` и образа статики
   `static` с боевыми адресами API. Образы публикуются в GitHub Container
   Registry под тегом версии.
3. Выкладка: по SSH на сервере запускается
   [`scripts/deploy.sh`](scripts/deploy.sh).

Скрипт выкладки на сервере:

- переводит рабочую копию на тег;
- определяет изменившиеся части через
  [`scripts/deploy-plan.sh`](scripts/deploy-plan.sh): служба перезапускается,
  только если изменился ее код, используемые ею пакеты или общие файлы
  сборки, поэтому выкладка консоли не прерывает виджет на сайтах клиентов;
- ждет конца синхронизации, если перезапускается ее обработчик;
- выгружает базу в `~/backups/reviews-predeploy`, где хранятся 5 последних
  выгрузок;
- загружает образы, а если образ недоступен, прекращает работу до каких-либо
  изменений;
- заменяет службы и ждет их готовности, затем ставит статику через
  [`scripts/install-static.sh`](scripts/install-static.sh) без перерыва в
  работе;
- проверяет ответы служб и nginx.

Если служба не пришла в рабочее состояние или проверка ответов не прошла,
замененные службы и статика возвращаются к прежней версии, а workflow
завершается ошибкой. Контейнер базы выкладка не трогает: изменения его
описания в `docker-compose.prod.yml` применяются вручную.

Развернутая версия записана в `~/.local/state/reviews-deploy/current-tag`,
журнал выкладок в `deploy.log` того же каталога.

### Откат

В GitHub: Actions, «Выкладка», Run workflow с тегом прежней версии. Прежний
тег выкладывается тем же порядком, что и новый. На сервере то же самое
делает команда из каталога сервиса:

```bash
./scripts/deploy.sh v1.1.0
```

После первой автоматической выкладки рабочая копия стоит на теге, а не на
ветке, поэтому `git pull` в ней больше не применяется.

### Настройка

Выполняется один раз.

1. Создать на своем компьютере отдельный ключ без пароля для GitHub Actions:

   ```bash
   ssh-keygen -t ed25519 -N '' -C github-actions-deploy -f reviews-deploy
   ```

2. Разрешить ключу на сервере только выкладку: дописать в
   `~/.ssh/authorized_keys` одну строку, где после префикса идет содержимое
   `reviews-deploy.pub`:

   ```text
   restrict,command="/home/deploy/apps/reviews/scripts/deploy.sh" ssh-ed25519 AAAA… github-actions-deploy
   ```

   `restrict` запрещает терминал и любые перенаправления, а `command`
   заменяет команду клиента запуском скрипта. Тег из workflow приходит в
   скрипт через `SSH_ORIGINAL_COMMAND`.

3. Получить ключ сервера для проверки его подлинности. Строка берется на
   самом сервере, а не через сеть:

   ```bash
   awk '{ print "45.146.166.181", $1, $2 }' /etc/ssh/ssh_host_ed25519_key.pub
   ```

4. В настройках репозитория на GitHub создать окружение `production`
   (Settings, Environments) и задать в нем:

   | Имя                  | Вид      | Значение                          |
   | -------------------- | -------- | --------------------------------- |
   | `DEPLOY_SSH_KEY`     | Secret   | содержимое файла `reviews-deploy` |
   | `DEPLOY_KNOWN_HOSTS` | Secret   | строка из шага 3                  |
   | `DEPLOY_HOST`        | Variable | `45.146.166.181`                  |
   | `DEPLOY_USER`        | Variable | `deploy`                          |

   Файл `reviews-deploy` после этого можно удалить: если ключ понадобится
   снова, проще выпустить новый. Адреса API для сборки заданы в workflow, а
   переменные репозитория `VITE_CONSOLE_API_URL` и `VITE_WIDGET_API_URL`
   переопределяют их при необходимости.

5. Один раз обновить рабочую копию на сервере, чтобы в ней появился скрипт
   выкладки:

   ```bash
   git fetch && git merge --ff-only origin/main
   ```

6. Поставить первый тег. Сборка опубликует образы приватными, и выкладка
   остановится на их загрузке, ничего не изменив. Четыре пакета
   (`reviews-console-api`, `reviews-widget-api`, `reviews-sync-worker`,
   `reviews-static`) нужно сделать публичными: на странице пакета Package
   settings, Danger Zone, Change visibility, Public. Решение необратимо, но
   образы не содержат секретов: все настройки приходят из `.env` на сервере.
   Затем в workflow выбрать Re-run failed jobs.

Первая выкладка обновляет все части, потому что прежняя версия неизвестна:
виджет на сайтах клиентов прервется на несколько секунд, пока
перезапускается `widget-api`.

## Резервное копирование

По расписанию сохраняется только база MongoDB. Дампы находятся в
`~/backups/reviews/reviews-*.archive.gz`: 14 последних архивов на сервере
и зашифрованные копии за 60 дней в Yandex Object Storage. Локальные архивы
содержат персональные данные и создаются с правами `600`.

Файл `.env`, nginx и Certbot копируются вручную после изменения настроек.
Существующие ручные копии в каталоге `reviews/config` бакета автоматическая
ротация базы не удаляет.

Метка `~/.local/state/reviews-backup/last-success` обновляется только после
успешной выгрузки дампа вне сервера и ротации в S3. Локальная копия перед
выкладкой эту метку не обновляет.

### Дамп базы

Отзывы, клиники и врачей можно заново загрузить из MyReviews, но восстановимо
не все содержимое базы. Ключ кабинета прописан в коде вставки на сайте
клиента, идентификаторы клиник и врачей стоят в атрибутах `target-id` на его
страницах, а условия отбора, скрытые записи, домены и учетная запись консоли
заданы вручную. Новая загрузка выдала бы записям новые идентификаторы, и
виджеты на сайте перестали бы работать.

Выгрузку выполняет [`scripts/backup-db.sh`](scripts/backup-db.sh). Скрипт
запускает `mongodump` внутри контейнера базы, поэтому учетные данные ему не
нужны. Старые архивы удаляются только после проверки нового:

- целостность сжатого потока проверяет `gzip -t`: обрезанный или поврежденный
  архив отвергается;
- `mongorestore --dryRun` проверяет заголовок и наличие кабинетов и целей;
  это не заменяет настоящее восстановление в отдельную тестовую MongoDB;
- хранятся 14 последних архивов, и неудачный запуск старые не удаляет;
- второй запуск, пока идет первый, завершается сразу.

| Переменная              | По умолчанию                                  | Назначение                              |
| ----------------------- | --------------------------------------------- | --------------------------------------- |
| `BACKUP_DIR`            | `~/backups/reviews`                           | Каталог архивов                         |
| `BACKUP_KEEP`           | `14`                                          | Сколько архивов хранить на сервере      |
| `MONGO_CONTAINER`       | `reviews-mongo`                               | Контейнер базы                          |
| `BACKUP_REMOTE`         | не задана                                     | Путь rclone для копии вне сервера       |
| `BACKUP_AGE_RECIPIENTS` | `~/.config/reviews-backup/age-recipients.txt` | Открытые ключи age для шифрования копии |
| `BACKUP_REMOTE_DAYS`    | `60`                                          | Сколько дней хранить копии вне сервера  |
| `BACKUP_STATE_DIR`      | `~/.local/state/reviews-backup`               | Метка успешной выгрузки вне сервера     |

Дамп снимается с работающей standalone MongoDB без `--oplog`. При
одновременной записи он не гарантирует общего момента времени для всех
коллекций. Расписание выбрано после ночной синхронизации; ручные изменения
и синхронизацию из консоли следует выполнять вне окна копирования.

### Выгрузка по расписанию

После настройки S3 и age сначала проверить запуск с копией вне сервера:

```bash
BACKUP_REMOTE=yandex:stackra-bucket/reviews ./scripts/backup-db.sh
cat ~/.local/state/reviews-backup/last-success
```

Затем поставить одно задание в crontab пользователя `deploy`:

```bash
install -d -m 700 ~/backups/reviews
crontab -e
```

```cron
# Дамп базы в 04:00, через час после ночной синхронизации.
0 4 * * * BACKUP_REMOTE=yandex:stackra-bucket/reviews /home/deploy/apps/reviews/scripts/backup-db.sh >> /home/deploy/backups/reviews/backup.log 2>&1
```

Время отсчитывается по часовому поясу сервера (Europe/Moscow). Каталог
создается заранее: cron открывает журнал до запуска скрипта, и без каталога
задание не выполнится. Старое задание без `BACKUP_REMOTE` нужно заменить
указанным выше, чтобы не создавать два ежедневных дампа. Итог каждого
прогона дописывается в `backup.log`. Дополнительные права sudo не требуются.

Проверка после первого запуска по расписанию:

```bash
cat ~/.local/state/reviews-backup/last-success
tail -n 50 ~/backups/reviews/backup.log
rclone lsf yandex:stackra-bucket/reviews --recursive
```

Метка показывает время последней успешной выгрузки вне сервера, а не попытки.
При ошибке ее прежнее значение сохраняется. Автоматические уведомления о
сбоях отдельно не настроены, поэтому свежесть метки и журнал нужно проверять.

Перед выкладкой скрипт запускается вручную из каталога сервиса:

```bash
./scripts/backup-db.sh
```

### Копия вне сервера

Если задана переменная `BACKUP_REMOTE`, каждый проверенный архив
дополнительно уходит в объектное хранилище S3 вне провайдера VPS, сейчас —
Yandex Object Storage. Выгрузку выполняет
[`scripts/upload-backup.sh`](scripts/upload-backup.sh):

- архив шифруется утилитой `age` открытым ключом, а закрытый ключ хранится
  только вне сервера, поэтому ключи хранилища не открывают доступа к данным;
- после выгрузки размер копии сверяется со списком объектов хранилища;
- дампы старше 60 дней удаляются только после успешной выгрузки нового;
  ротация затрагивает только имена `reviews-*.archive.gz.age`;
- сбой выгрузки не отменяет локальный архив, а в журнал записывается команда
  для повтора.

Настройка выполняется один раз.

1. Создать приватный бакет стандартного класса в Yandex Object Storage.
   Создать сервисный аккаунт в том же каталоге, выдать ему `READ` и `WRITE`
   через ACL этого бакета и создать статический ключ доступа. Сохранить
   идентификатор и секретный ключ в менеджере паролей.
2. Установить утилиты на сервере:

   ```bash
   sudo apt install rclone age
   ```

3. Описать хранилище для rclone. Ключи вписываются в файл, а не в командную
   строку, чтобы не попасть в историю оболочки:

   ```bash
   install -d -m 700 ~/.config/rclone
   umask 077
   nano ~/.config/rclone/rclone.conf
   chmod 600 ~/.config/rclone/rclone.conf
   ```

   ```ini
   [yandex]
   type = s3
   provider = Other
   env_auth = false
   access_key_id = <ключ доступа>
   secret_access_key = <секретный ключ>
   region = ru-central1
   endpoint = https://storage.yandexcloud.net
   no_check_bucket = true
   ```

   `no_check_bucket` позволяет обойтись без прав на создание бакетов.
   Проверка: команда `rclone lsf yandex:stackra-bucket` завершается без ошибки.

4. Создать пару ключей age на своем компьютере, а не на сервере (на macOS
   утилита ставится через `brew install age`):

   ```bash
   mkdir -p ~/.config/clinicstars
   chmod 700 ~/.config/clinicstars
   umask 077
   age-keygen -o ~/.config/clinicstars/reviews-backup.agekey
   age-keygen -y ~/.config/clinicstars/reviews-backup.agekey > ~/.config/clinicstars/age-recipients.txt
   ```

   Дополнительную копию закрытого ключа сохранить в менеджере паролей.
   На сервер передать только открытый ключ, строку `age1…`. Из терминала Mac:

   ```bash
   ssh deploy@153.80.40.79 'install -d -m 700 "$HOME/.config/reviews-backup"'
   scp ~/.config/clinicstars/age-recipients.txt deploy@153.80.40.79:.config/reviews-backup/age-recipients.txt
   ```

5. Проверить выгрузку вручную:

   ```bash
   BACKUP_REMOTE=yandex:stackra-bucket/reviews ./scripts/backup-db.sh
   ```

6. Настроить ежедневный запуск по инструкции выше.
   `BACKUP_REMOTE` передается в окружении команды; файл `.env` скрипты
   не загружают и не копируют. Первые ручные файлы `reviews-env-*.env.age` и
   `reviews-nginx-*.tar.gz.age` автоматическая ротация не удаляет.

### Восстановление

На время восстановления останавливаются консольный API и обработчик
синхронизации, чтобы не писать в базу одновременно с `mongorestore`.
Ключ `--drop` заменяет коллекции
содержимым архива, поэтому изменения, сделанные после выгрузки, теряются.

```bash
docker compose -f docker-compose.prod.yml stop console-api sync-worker
docker exec -i reviews-mongo sh -c 'mongorestore -u "$MONGO_INITDB_ROOT_USERNAME" -p "$MONGO_INITDB_ROOT_PASSWORD" --authenticationDatabase admin --archive --gzip --drop --stopOnError' < ~/backups/reviews/reviews-ГГГГ-ММ-ДД-ЧЧММСС.archive.gz
# Только после успешного восстановления:
docker compose -f docker-compose.prod.yml start console-api sync-worker
```

Если сервер потерян, архив берется из хранилища. Закрытый ключ age на сервер
не копируется: копия скачивается через файловый менеджер бакета в панели
Yandex Cloud или командой `rclone copyto`, расшифровывается на своем компьютере, и
на сервер передается уже готовый архив.

```bash
umask 077
age -d -i ~/.config/clinicstars/reviews-backup.agekey -o reviews.archive.gz reviews-ГГГГ-ММ-ДД-ЧЧММСС.archive.gz.age
gzip -t reviews.archive.gz
```

Ручные копии `.env` и nginx из `reviews/config` расшифровываются тем же
ключом на своем компьютере. Например, для ранее сохраненного архива nginx:

```bash
umask 077
age -d -i ~/.config/clinicstars/reviews-backup.agekey -o nginx-certbot.tar.gz reviews-nginx-ГГГГ-ММ-ДД-ЧЧММСС.tar.gz.age
tar -tzf nginx-certbot.tar.gz
```

Ручные копии настроек нужно обновлять после изменений. При восстановлении
`.env` возвращается в каталог проекта с правами `600`, а системные настройки —
в соответствующие каталоги после проверки путей, пользователей и версий
пакетов. Архив nginx включает все проекты сервера, поэтому файлы для
восстановления одного проекта выбираются отдельно. Без сохраненного
`TOKEN_ENCRYPTION_KEY` токен MyReviews из базы не расшифровать.

Локальные архивы защищают от ошибок в данных и неудачной выкладки, S3 у
другого провайдера — от потери VPS. Закрытый ключ age хранится отдельно от
сервера и бакета. Резервные копии всего бокса у Sprintbox дополняют эти
архивы. Полную настройку чистого сервера нужно проверять отдельно; она
будет автоматизирована через Ansible.

Проверки скриптов без сети и боевых данных запускаются командой
`python3 -B scripts/tests/test_backups.py` и включены в workflow выкладки.
Они подставляют Docker, age и S3, проверяя целостность архивов,
права, ротацию, обработку ошибок и метку успеха. При установленном age
дополнительно проверяется настоящее шифрование и расшифровка. Полное
восстановление MongoDB дополнительно проверяют на копии из бакета.

## Как работает синхронизация

Полный прогон выполняется дважды в сутки, в 03:00 и 15:00 по Москве (часовой
пояс задан явно, время контейнера значения не имеет). Запрос из консоли
подхватывается опросом раз в 15 секунд.

Прогон защищен от потери данных: захват не дает двум процессам работать над
одним кабинетом, за один раз нельзя удалить больше половины отзывов, а пустой
ответ агрегатора при непустой базе прерывает прогон вместо очистки.
